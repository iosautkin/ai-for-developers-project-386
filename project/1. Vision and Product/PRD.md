# PRD: «Календарь звонков»

**Статус:** согласовано  
**Слой документации:** 1. Vision and Product  
**Версия:** 1.1  
**Дата:** 2026-08-05

## 1. Цель проекта и видение продукта

Главная цель проекта — учебная: пройти полный цикл Design First-разработки небольшого веб-приложения с помощью ИИ-агентов. Результат должен последовательно пройти от продуктовых требований и UX-сценариев через API- и модульные контракты к независимо реализованным фронтенду, бэкенду, e2e-тестам, автоматизации релизов, запуску в Docker-контейнере и публичному деплою.

Реализуемый продукт — «Календарь звонков», упрощённый сервис записи на встречу по мотивам Cal.com. Один заранее заданный владелец публикует типы встреч, а гости без регистрации выбирают тип, находят свободное время и бронируют звонок.

Проект намеренно ограничен требованиями учебных материалов и решениями, явно зафиксированными в этом PRD. Возможности полноценного коммерческого сервиса не добавляются без отдельного требования.

## 2. Источники требований

При расхождении исходных материалов используется следующий приоритет:

1. Явные решения, согласованные и зафиксированные в этом PRD.
2. `Lesson2.txt` — подробные продуктовые правила и роли.
3. `Lesson1.txt` — общее описание продукта и учебного процесса.
4. `Lesson3.txt`–`Lesson6.txt` — требования к реализации фронтенда, бэкенда, интеграционным проверкам, релизам, Docker и деплою.
5. Примеры экранов и Cal.com — UX-референсы, но не самостоятельный контракт поведения.

Рекомендации уроков по конкретным инструментам и платформам не становятся продуктовым контрактом автоматически. Они считаются обязательными только там, где соответствующий выбор явно зафиксирован в документации проекта. Уроки задают обязательный минимум; явно согласованные решения могут усиливать его, если не добавляют несогласованные продуктовые функции.

Детальные сценарии, UI-элементы и состояния относятся к слою `2. Spec, UX and Test Cases`. API, типы сущностей и контракты модулей относятся к слою `3. Architecture`.

## 3. Пользователи

### 3.1. Владелец календаря

Один заранее заданный профиль. Владелец не регистрируется и не авторизуется. Он создаёт и просматривает типы встреч, а также просматривает единый список предстоящих бронирований.

### 3.2. Гость

Посетитель публичной части приложения. Гость не создаёт аккаунт и не авторизуется. Он выбирает тип встречи, свободное время и создаёт бронирование, указав свои данные.

## 4. Решаемая задача

Без сервиса владелец и гость вынуждены вручную согласовывать формат и время звонка, а параллельные договорённости могут привести к конфликтам.

«Календарь звонков» предоставляет линейный самостоятельный путь записи и единое правило занятости календаря:

- гость видит доступные типы встреч и свободное время;
- гость создаёт запись без регистрации и переписки;
- система не допускает пересекающихся бронирований;
- владелец видит все будущие встречи в одном месте.

## 5. Основные пользовательские сценарии MVP

### 5.1. Бронирование гостем

1. Гость открывает главную страницу.
2. Переходит в каталог типов встреч.
3. Выбирает тип встречи и видит его название, описание и длительность.
4. Выбирает доступную дату в окне записи.
5. Выбирает свободное время.
6. Указывает обязательные имя и email и при необходимости добавляет заметку.
7. Подтверждает бронирование.
8. Получает экран успешного результата либо понятное сообщение о конфликте или ошибке.

### 5.2. Создание типа встречи владельцем

1. Владелец открывает административную часть приложения.
2. Создаёт тип встречи, задавая идентификатор, название, описание и длительность.
3. Новый тип встречи сохраняется и появляется в публичном каталоге.

### 5.3. Просмотр предстоящих встреч владельцем

1. Владелец открывает административную часть приложения.
2. Видит единый список будущих бронирований всех типов встреч.
3. Встречи отсортированы от ближайшей к более поздним.
4. Для каждой встречи доступны тип, дата, время, имя, email и заметка гостя.

## 6. Продуктовые требования MVP

| ID | Требование |
| --- | --- |
| PR-01 | Приложение должно иметь публичную часть для гостя и административную часть для владельца. |
| PR-02 | Приложение должно использовать один заранее заданный профиль владельца. |
| PR-03 | Публичный путь должен включать главную страницу, каталог типов встреч, выбор даты и времени, ввод данных гостя и результат бронирования. |
| PR-04 | Владелец должен иметь возможность создавать и просматривать типы встреч. |
| PR-05 | Тип встречи должен содержать идентификатор, название, описание и длительность в минутах. |
| PR-06 | Длительность типа встречи должна быть кратна 15 минутам и находиться в диапазоне от 15 до 540 минут включительно. |
| PR-07 | Публичный каталог должен показывать все созданные типы встреч с названием, описанием и длительностью. |
| PR-08 | Если типы встреч отсутствуют, каталог должен показывать пустое состояние без перехода в административную часть. |
| PR-09 | Для выбранного типа встречи гость должен видеть доступное время в окне из 14 календарных дат: текущая дата по Москве и следующие 13 дат. |
| PR-10 | Время начала доступных интервалов должно формироваться с шагом 15 минут. |
| PR-11 | Гость должен иметь возможность выбрать только ещё не наступивший свободный интервал, который полностью помещается в рабочее расписание. |
| PR-12 | Для бронирования гость должен указать имя и email; заметка является необязательной. |
| PR-13 | Бронирования владельца не должны пересекаться, даже если относятся к разным типам встреч. Соприкосновение времени окончания одной встречи со временем начала другой допустимо. |
| PR-14 | Защита от двойного бронирования должна обеспечиваться бэкендом. Из конкурирующих попыток занять один интервал успешно завершается не более одной. |
| PR-15 | Если выбранный интервал уже занят, бронирование не создаётся; гость получает объяснение и обновлённый список свободного времени. |
| PR-16 | После успешной записи приложение должно показать тип и длительность встречи, дату, время начала и окончания, имя гостя и имя владельца. |
| PR-17 | Владелец должен видеть единый список предстоящих бронирований всех типов встреч, отсортированный по возрастанию времени начала. |
| PR-18 | Для предстоящей встречи административная часть должна показывать тип встречи, дату, время начала и окончания, имя, email и заметку гостя. |
| PR-19 | Главная страница, каталог, бронирование и административная часть не должны требовать регистрации или авторизации. |
| PR-20 | Профиль владельца, созданные типы встреч и бронирования должны сохраняться после перезапуска приложения. |
| PR-21 | Начальные типы встреч не создаются автоматически: пустой календарь заполняется владельцем. |

## 7. Правила календаря и доступности

### 7.1. Рабочее расписание

- Часовой пояс приложения: московское время (`Europe/Moscow`).
- Рабочие дни: понедельник–пятница.
- Рабочее время: `09:00–18:00`.
- Пользовательская настройка расписания отсутствует.
- Все даты и время показываются по Москве без определения часового пояса браузера и автоматической конвертации.
- На экране выбора времени должно быть явно указано, что время московское.

### 7.2. Правило доступного интервала

Интервал доступен для бронирования, только если одновременно выполнены все условия:

1. Время начала находится на 15-минутной сетке.
2. Время начала ещё не наступило по Москве; отдельного минимального срока до встречи нет.
3. Дата входит в окно записи из 14 дат.
4. Встреча целиком помещается между `09:00` и `18:00` рабочего дня.
5. Встреча не пересекается ни с одним существующим бронированием владельца.

Например, при окончании рабочего дня в `18:00` встреча длительностью 30 минут не может начаться в `17:45`. Встречи `10:00–10:30` и `10:30–11:00` допустимы, поскольку их интервалы не пересекаются.

## 8. Данные и сохранение

### 8.1. Предустановленные данные

- В приложении существует один предустановленный профиль владельца.
- Начальные типы встреч отсутствуют.

### 8.2. Постоянные данные

После перезапуска приложения должны сохраняться:

- профиль владельца;
- созданные типы встреч;
- бронирования, включая данные гостя и заметку.

Конкретная модель данных и технология хранения определяются в слое `3. Architecture`.

`Lesson4.txt` допускает in-memory-хранилище и сброс данных после перезапуска как достаточный учебный минимум. Для этого проекта отдельно согласовано усиленное требование: профиль владельца, типы встреч и бронирования должны сохраняться после перезапуска приложения.

## 9. UX-направление

Примеры из `0. Context` задают рекомендуемый, но не обязательный визуальный подход:

- отдельная главная страница с переходом к записи;
- каталог типов встреч в виде карточек;
- экран бронирования, на котором одновременно понятны тип встречи, календарь и состояния времени;
- визуальное различие свободных и занятых интервалов;
- невозможность продолжить сценарий до выбора допустимого времени;
- отдельные состояния успешного результата, конфликта и пустого каталога.

Интерфейс реализуется на React и Mantine UI. Интерактивные примеры экранов, компонентов и состояний создаются в Storybook в слое `2. Spec, UX and Test Cases`; там же фиксируются маршруты, тексты, валидация полей и идентификаторы из `UIElements.ts`.

## 10. Границы MVP

### 10.1. Входит в MVP

- Один предустановленный владелец.
- Главная страница и публичный каталог типов встреч.
- Создание и просмотр типов встреч владельцем.
- Выбор гостем типа встречи, даты и времени.
- Создание и постоянное хранение бронирования.
- Единый список предстоящих встреч владельца.
- Защита от пересекающихся и конкурентных бронирований.
- Явные состояния успешной записи, конфликта и отсутствия типов встреч.

### 10.2. Не входит в MVP

- Регистрация, авторизация и личные кабинеты.
- Несколько владельцев и командные календари.
- Редактирование, удаление, скрытие и изменение порядка типов встреч.
- Настройка рабочего расписания через UI.
- Отмена, перенос и изменение статуса бронирования.
- Повторяющиеся встречи.
- Интеграции с внешними календарями и видеосвязью.
- Email-, SMS- и push-уведомления, календарные приглашения.
- Оплата.
- Автоматическое определение и пользовательское переключение часового пояса.
- Пользовательские настройки локализации и формата времени.

## 11. Критерии успеха учебного MVP

Бизнес-KPI, продуктовая аналитика и метрики роста для проекта не требуются. Проект считается успешным, когда:

1. Требования представлены последовательными слоями документации.
2. Основные сценарии формализованы в Gherkin, UI-элементы имеют сквозные идентификаторы из `UIElements.ts`, а доменные сущности представлены Mermaid-диаграммой в слое `2. Spec, UX and Test Cases`.
3. Экраны, компоненты и их состояния представлены интерактивными примерами в Storybook на Mantine UI.
4. Контракт фронтенда и бэкенда описан в TypeSpec.
5. Публичные интерфейсы TypeScript-модулей и компонентов описаны в `.d.ts`-контрактах.
6. Фронтенд и бэкенд реализованы раздельно, взаимодействуют только через согласованный API, а фронтенд корректно работает с отдельно запущенным бэкендом.
7. E2E-проверки в реальном браузере покрывают бронирование гостем, создание типа встречи, список владельца, пустой каталог и конфликт занятого слота.
8. Пересекающееся или конкурентное бронирование не приводит к двойной записи.
9. Основные сценарии покрыты проходящими e2e-тестами со сквозной трассируемостью до спецификации и UI-идентификаторов.
10. Все non-merge коммиты соответствуют Conventional Commits; CI проверяет их с помощью стандартной конфигурации `@commitlint/config-conventional`. Локальные commit hooks не требуются.
11. GitHub Actions workflow с `release-please` создаёт или обновляет release-PR с changelog и предлагаемой версией по Semantic Versioning.
12. Приложение собирается в Docker-образ, автоматически запускается в контейнере и слушает порт из переменной окружения `PORT`.
13. Приложение опубликовано по публичной ссылке без обязательной привязки к конкретной платформе, а актуальная ссылка добавлена в корневой `README.md`.

## 12. Известное ограничение учебной модели

Административная часть не защищена авторизацией, но показывает email и заметки гостей. Это осознанное ограничение учебного MVP, напрямую следующее из условия об отсутствии авторизации. Такое решение непригодно для production-сервиса без контроля доступа и дополнительных мер защиты персональных данных.
