Этот учебный проект "Календарь звонков" на typescript, react и Mantine UI является реализацией разделов 0-3 документации в ./project
Сама реализация проекта должна быть в разделе 4. Implementation

Документация делится на слои, от верхнего к нижнему:
0. Context - сырой контекст, может содержать любые файлы полезные для проекта
1. Vision and Product - краткое описание видения, продукта и его цели
2. Spec, UX and Test Cases - Подробное описания функциональности и e2e тестовых сценариев и UX/UI
3. Architecture - архитектура, контракты и спецификации модулей
4. Implementation - реализация приложения

Можно ссылаться на верхние слои из нижних, также можно импортировать что-либо из верхних слоев в нижние


2. Spec, UX and Test Cases - как должен быть организован раздел
В папке должен быть перечень всех UI элементов в виде TypeScript enum в runtime-файле UIElements.ts
```
// пример UIElements.ts
export enum UIElements {
  // кнопка сабмита логина
  LOGIN_SUBMIT_BUTTON = 'login-submit-button',
  // инпут имейла логина
  LOGIN_EMAIL_INPUT = 'login-email-input',
  // навигационная панель
  NAVIGATION_BAR = 'navigation-bar',
  // баннер ошибки
  ERROR_BANNER = 'error-banner',
}
```
Эти id должны использоваться в сценариях, дизайне, архитектуре, автотестах (как data test id), имплементации для сквозной трассируемости

Сценарии:
- должны храниться в формате Gherkin (BDD)
- должны иметь идентификаторы
- должны использовать id из UIElements.ts, если описывают взаимодействие с UI

Дизайны:
- Storybook в этом проекте заменяет дизайн в Figma и является обязательным интерактивным источником дизайна
- должны быть в форме storybook, с экранами, компонентами и их состояниями, с переходами между ними в сторибуке по кликам
- должны использовать библиотеку Mantine UI
- должны импортировать id элементов из UIElements.ts
- должны использовать захардкоженные, а не динамические данные, чисто для примера. Кроме переиспользуемых компонентов. В реализации (4. Implementation) уже настоящие динамические данные должны быть и настоящая логика
- не должно быть сложной логики в компонентах сторибука, просто верстка и переходы между состояниями. Это только примеры для демострации дизайна юзеру и разработчику, а не настоящая реализация
- JSX и логика Storybook-дизайнов не импортируются в реализацию. CSS Modules и дизайн-токены можно выборочно импортировать в реализацию через alias `@design`

Диаграмма доменных сущностей в формате mermaid


3. Architecture - как должен быть организован раздел
Раздел должен содержать:
- информацию о стеке и архитектуре
- контракт между фронтендом и бэкендом приложения, в виде typespec спецификации
- все типы сущностей и эндпоинтов
- границы системы, архитектурные решения и потоки данных



4. Implementation - содержит реализацию
Также содержит e2e автотесты, они должны имортировать id из UIElements.ts и ссылаться на сценарии и/или UI из спеки
Содержит фронтенд и бэкенд в отдельных папках frontend и backend

Дерево контрактов и спек TypeScript-модулей хранится в этом разделе: контракты находятся непосредственно рядом со своими реализациями в `4. Implementation`.
Каждый собственный production-модуль, UI-компонент, hook, route, service и repository должен иметь соседний контракт с именем `*.contract.d.ts`.
Реализация связывается с таким контрактом через `import type`.
Контракты не требуются для тестов, Storybook stories, конфигурационных и сгенерированных файлов.

Пример спеки модуля:
someModule.contract.d.ts
```
/* 
  Модуль должен использовать именно эту зависимость, но в реализации могут быть и дополнения.
  В реализации уже должен быть импорт реализации someModuleB.ts, а не someModuleB.d.ts. Но интерфейс d.ts тоже можно импортировать при необходимости 
*/
import { SomeModuleB } from "./someModuleB.d.ts";

/**
  Описание роли и функциональности модуля в целом
  Ссылки на разделы документации, сценариев и дизайна, которые реализует модуль, в том числе id из UIElements.ts для UI компонентов
  Сценарии и контракты его использования, как он использует свои зависимости (делает то-то используя SomeModuleB)
*/

/**
  Описание роли и функциональности конкретно этого экспорта
*/
export type SomeModuleExportA = {}; // публичный интерфейс

/**
  Описание роли и функциональности конкретно этого экспорта
*/
export type SomeModuleExportB = {}; // публичный интерфейс

```
